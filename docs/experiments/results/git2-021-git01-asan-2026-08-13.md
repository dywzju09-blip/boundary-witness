# git2 GIT-01（Rebase checkout progress 回调 UAF）ASan 出证完成

- 日期：2026-08-13
- 前置：git2-021-git01-judgement-2026-08-13.md（判定层：guard=owner_holds_callback_bridged）
- 状态：**GIT-01 完整证据链闭合**——生成器自动产出的 harness 在 ASan 下报

## 1. 根因定位：原 harness 的 rebase 参数构造无效（缺证 ≠ 证伪）

判定层完成后（9f8a343），自动生成的 harness 运行 exit=0 无 ASan 报告，但
CALLBACK-INVOKED 已打印。用带时序标记的调试 harness 定位：

```text
CALLBACK-INVOKED        ← git_rebase_init 期间（rebase_init_merge → git_checkout_tree）
MARK-1 after-rebase-init
MARK-2/3 drop(opts)
MARK-4/5 drop(referent)
MARK-6 before-next
MARK-7 after-next       ← next() 不再调用回调
```

**progress 回调在 init 阶段就被调用（内存全部有效），next() 没有触发晚调**。查
libgit2 源码确认：`rebase_init_merge` 在 init 时执行 `git_checkout_tree`（用
`rebase->options.checkout_options`，payload 有效）；`next()` 的
`rebase_next_merge` 会再次 checkout——但只有当 rebase operations 非空且工作区
有实际变更时。

原 adapter 的 register_template 是
`repo.rebase(None, None, Some(&branch), Some(&mut opts))`——branch=None、
upstream=None、onto=branch 自身 → rebase_init_operations 产出**空 operations**
→ next() 直接 ITEROVER，永远不 checkout。**回调被调用但无 UAF 报告的原因是
harness 的 trigger 槽位没有构造出有效晚调，不是候选被证伪。**

## 2. adapter 修复（属缺陷修复，附理由）

`adapters/git2/rebase_checkout_progress.toml`：

| 槽 | 修改 | 理由 |
| --- | --- | --- |
| setup.two_commits | 两个 commit 各带 `a.txt`（v1→v2）文件差异 | 无文件差异时 checkout 无实际操作，progress 不触发 |
| register_template | `repo.rebase(Some(&branch), Some(&upstream), None, ...)`，upstream = HEAD 的 parent commit | 构造非空 operations 的有效 rebase；原参数把 onto 指向 branch 自身 |
| teardown | 增加 `drop(upstream)` | upstream 持有 `&repo` 借用，不先 drop 则 `drop(repo)` 编译失败 |

修复后重新生成 harness-rebase10（`bw generate-witness-harness` 全自动，无手工
编辑），ASan 出证。

## 4. 负对照（因果矩阵）

| 变体 | 修改 | ASan | 说明 |
| --- | --- | --- | --- |
| vulnerable | 原样 | **heap-use-after-free** | 晚调 + 失效同时发生 |
| no-trigger | 删 `rebase.next()` | 干净（exit=0） | 证明晚调是触发条件 |
| no-invalidate | 不 `drop(opts)` / `drop(referent)` | 干净（exit=0） | 证明失效是必要条件 |

**注意**：GIT-01 形状下 GIT-02 的「owned 变体」不适用——GIT-01 的闭包以
`Box<dyn FnMut>` 存进 CheckoutBuilder 字段，`drop(opts)` 释放闭包载体本身；
即使回调不访问 referent，外部经 payload 调用已释放的闭包对象（读 vtable）仍是
UAF。因此干净对照取 no-invalidate（交付载体存活），而不是 owned。这已被
no-invalidate 变体干净的结果支持。

## 6. 证明了什么 / 没证明什么

**证明了**：

- GIT-01 是真 UAF：`CheckoutBuilder::progress` 回调经 `RebaseOptions` 桥接到
  libgit2 后，`drop(opts)` 释放闭包载体，`rebase.next()` 仍调用 → 堆 UAF，
  ASan 独立 oracle 确认，trace 完整到 libgit2 C 侧（rebase_next_merge）。
- 生成器（非手工 harness）在修复后的 adapter 上能自动产出可出证的 harness；
  回调模板 `let _ = witness_referent.len()` 未被 DCE，与 GIT-02 一致。
- 因果矩阵成立：晚调（no-trigger 干净）与失效（no-invalidate 干净）都是 UAF
  的必要条件。

**没证明**：

- 未证明 libgit2 语义中「rebase options 的 checkout payload 存活期」与 Rust
  wrapper 的 Drop 语义**总是**冲突——只证明了在
  `rebase → drop(opts) → next()` 这一合法客户端序列下可稳定触发；其他序列
  （如 abort、多 operation、带 merge conflict）未测。
- 未证明外部侧 IR 能自动判定「bridged payload 被晚调」——本次的晚调存在性由
  libgit2 C 源码人工确认（rebase_next_merge → git_checkout_index），自动 IR
  证据未补（与 GIT-01 判定层文档的「外部侧未做独立 IR 证明」同一缺口）。
- 未做「不 drop referent 只 drop opts」的单变量对照（预期闭包载体 UAF 仍触发；
  因该变体与 no-invalidate 的边界意义有限，未跑）。
- git2 无「fixed 版本」对照：git2 0.21 之后版本是否改了 RebaseOptions /
  CheckoutBuilder 的持有语义未核查，GIT-01 不按 nday fixed-pair 断言。
